# MeshCloud v0.3 – Security and Network Architecture

This is an implementation plan and testable shared-core specification, **not a public P2P service**.

## Storage encoding

`Codec(k, m)` uses systematic Reed-Solomon erasure coding over GF(256), with a Cauchy parity matrix. Each stripe consists of `k` original fragments and `m` recovery fragments; any `k` intact, CID-verified fragments can reconstruct the stripe. Input shard length is at most 64 KiB, so large files require consecutive streaming stripes. No file length limit is imposed by the codec.

| Parameters | Total fragments | Max independently lost fragments | Redundancy overhead |
| --- | ---: | ---: | ---: |
| 10+10 | 20 | 10 | 2x |
| 10+20 | 30 | 20 | 3x |
| 10+100 | 110 | 100 | 11x |

These guarantees apply to **lost fragments**, not any arbitrary group of 100 consoles. To survive 100 offline consoles, placement must ensure that each of 110 fragments is on a DIFFERENT independent console or fault domain; two fragments lost on one node count as two. If 100 consoles out of 110 fail, the last 10 must contain the last 10 available fragments. Real node placement, fault-domain diversity, repair scheduling and bandwidth controls are not yet implemented.

Each reconstruction checks the authenticated CID for every available fragment before it is used. CIDs themselves only ensure integrity relative to the supplied manifest: the manifest MUST be signed/authenticated by the actual publisher. Do not accept shard CIDs from arbitrary unauthenticated peers.

The existing v0.2 local vault continues to store encrypted 4 MiB chunks. The new codec is an independently tested module; **it is not yet wired into vault uploads or any peer exchange**.

## Membership: enforced before EVERY request

Mandatory for all users and all platforms: at least 10 GiB (10,737,418,240 bytes) offered AND 10 GiB independently audited usable capacity. Never trust a client-side checkbox, quota value, reported free space, claimed auditor count or sparse placeholder file.

`src/admission.cpp` checks a short-lived (maximum one hour) Ed25519 signed ticket using a quorum of at least 3 independently pinned auditor public keys, all distinct. Each auditor signs canonical versioned byte fields: peer's Ed25519 public key, random ticket ID, offered size, independently audited size, issue time, expiry, and protocol version. The node signs a session transcript including its ticket hash, a fresh verifier-generated 32-byte challenge and a 32-byte authenticated channel-exporter secret (such as a TLS 1.3 exporter). Zero binders, invalid signatures, a compromised quorum, self-signed, stale or undersized tickets fail.

**Critical caveat:** A quorum signature is only meaningful if auditor nodes ACTUALLY verify 10 GiB remotely using a well-designed proof-of-storage challenge and prevent sham/fake capacity. No auditing or issuer/network enrollment is available yet. The admission verification code deliberately contains **no self-issue command, embedded auditor keys or default-trust roots**. Production auditors must be governed, key-rotated, Sybil-resistant, audited, and deliberately distributed, with offline revocation handling. Never ship test private keys or allow arbitrary clients to select their own trusted auditors.

`src/wire.cpp` encodes framed operations: `MCP1`, version 1, operation, reserved bytes (zero), big-endian length and payload. The parser rejects oversized/truncated/unknown frames and authorizes each operation against an `AuthenticatedPeer` handle that can only be created by the quorum verification function. The parser also checks that the exact nonce and authenticated exporter match the verified session; a client-provided boolean admission object cannot be passed into network dispatch. Maximum frame payload is 4 MiB plus 4096 bytes. Importantly, these frames are **not encrypted or authenticated on their own**: they MUST run inside a channel established by secure transport and a successfully verified member handshake. The server must never accept `VerifiedMembership` booleans sent over the wire.

## Private-IP threat model

Relay-only routing is planned to avoid disclosing *peer-to-peer* source IPs between endpoints. Relays can still see connection IPs, timing, traffic size, and node IDs; relay operators should be independently operated and accountable. TLS/Noise session channel binders must be generated by a real authenticated transport. No software can honestly promise that your IP remains unseen by every intermediary.

## Retention and cleanup

The local vault already expires an unused file after 90 consecutive days. Any *complete, hash-verified* restore refreshes the deadline by 90 days; searches, failed transfers, and partial restores do not. Distributed TTL will need a publisher-authorized file-retention policy, authenticated complete-download receipts (preventing popularity spoofing), cross-node clock handling, fragment repair, expiration gossip and safe garbage collection. A central admin is not required in the design, but implementation must not invent consensus/availability.

## Next required production work

1. A real peer-to-peer secure transport over relays (e.g. libp2p Noise/TLS 1.3), with fresh nonce and validated channel binding.
2. Storage-audit challenge/response with disk-backed evidence, anti-Sybil behavior, independent auditor quorum and revocation.
3. Durable signed manifests, CID resolver, member-only decentralized search, chunk streaming protocol, retry/resume and backpressure.
4. Integrate the erasure codec with encrypted upload streams, independent node placement, replica lease tracking and automatic repairs.
5. Multi-node integration/fault-injection testing; native PS5 build adapter, filesystem path handling and UI.
6. Operations/security review, abuse response, crash consistency and privacy documentation.

Never enable public Internet admission purely by setting booleans in a client. The present release remains a **pre-alpha**.
